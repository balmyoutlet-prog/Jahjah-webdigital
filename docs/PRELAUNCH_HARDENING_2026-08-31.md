# Jahjah WebDigital — Zero-Lovable-Credit Pre-Launch Hardening

Date: 2026-08-31 · Branch: `claude/jahjah-prelaunch-hardening-yv499g`
All changes made directly via code edits + committed SQL migration — no Lovable AI agent/chat/generation credits used, no money spent, no domains purchased, no paid APIs enabled.

## What changed

1. **Contact form** (`src/components/site/ContactForm.tsx`, `src/lib/contact.functions.ts`, migration `inquiries` table) — real server-side submission with Zod validation, honeypot + timing spam checks, and a DB-backed rate limit. Success/error states in the UI. Instagram/WhatsApp now appear as **fallback links after a successful submission**, not the only path — no `window.open`/clipboard dependency, so it works on iPhone Safari without popups.
2. **SSRF hardening** (`src/lib/net/ip-guard.ts`, rewritten `src/lib/leads/audit.server.ts`) — http/https only, credentials-in-URL rejected, DNS resolved via DoH with every resolved IPv4/IPv6 address checked against private/loopback/link-local/multicast/reserved/CGNAT/documentation/cloud-metadata ranges, manual redirect loop (max 3 hops, every hop re-validated), 8s timeout, 400KB body cap. Documented residual limitation: Cloudflare Workers' `fetch()` does its own DNS resolution with no IP-pinning API, so a narrow DNS-rebinding window remains — noted in code, not hidden.
3. **Rate limiting** (`src/lib/rate-limit.server.ts`, `check_rate_limit` Postgres function) — atomic, zero-cost, DB-backed fixed-window limiter applied to both public lead-capture endpoints (business lookup + contact form).
4. **Publish → real state machine** (`src/lib/platform.functions.ts`, `src/routes/_authenticated/admin.domains.tsx`, `dashboard.tsx`) — `domain_status` gained `requested/verified/dns_pending/dns_configured/tls_active/live/failed`; `project_status` gained `launch_requested`. The customer action is now "Request Launch," which only ever sets `launch_requested` — never `published`. New admin-only functions (`adminVerifyDomainOwnership`, `adminUpdateDomainStage`, `adminMarkDomainFailed`, `adminVerifyAndGoLive`) let an admin manually verify a domain and stage DNS/TLS work; `published`/`published_at`/`published_domain` are set **only** after `adminVerifyAndGoLive` gets a real, successful HTTPS response from the domain (reusing the SSRF-hardened fetch).
5. **Privacy page** (`src/routes/privacy.tsx`) — describes only what's actually collected today (contact inquiries, CRM/prospect research, Supabase auth/storage, Whish payment submissions, first-party session analytics, spam-protection IP use). Linked from the footer and the onboarding consent line, alongside Terms.
6. **SEO** (`src/lib/seo.ts`, all public route heads, `robots.txt`, `sitemap.xml`) — canonical/og:url now resolve through a `SITE_URL`-driven helper: relative today (no domain connected yet — never fabricated), automatically absolute the moment `SITE_URL`/`VITE_SITE_URL` is set. Added `og:image`/`twitter:image` pointing at a real rendered brand card (`public/images/og-cover.png`, built with headless Chromium from the site's own colors/type, not a stock image). Rebuilt `sitemap.xml` with all seven indexable pages (`/`, `/work`, `/process`, `/packages`, `/contact`, `/terms`, `/privacy`) and a note to switch to absolute URLs once the domain is live; `robots.txt` now references it. `/_authenticated` (dashboard/admin/onboarding) now carries `noindex, nofollow`.
7. **Link/button audit** — fixed homepage "See how we work" → `/process` (was `/work`). Scanned every `<a>`/`<Link>`/`<button>` for dead hrefs, missing `rel` on `target="_blank"`, and buttons defaulting to `type="submit"` inside a form; found none beyond the one intentional fix. Added Escape-to-close + initial focus to the one modal (`LeadLightbox`) that lacked it.
8. **Build hygiene** — fixed the only real TypeScript errors in new code (`ip-guard.ts` strict-null cases) and the only lint errors in new files (`no-explicit-any` in `seo.ts`, `admin.domains.tsx`, `admin.inquiries.tsx`). Left ~60 pre-existing `no-explicit-any` lint errors and one pre-existing `prefer-const` error untouched in files outside this task's scope (confirmed pre-existing by diffing against origin/main; fixing them broadly was out of scope for a security/hardening pass and risked unrelated regressions).

## What could NOT be verified in this session, and why

- **Migration not applied to the live database.** `supabase/migrations/20260831120000_prelaunch_hardening.sql` is committed but this session's Supabase MCP connector is authorized against a *different* Supabase project (`zmrivcvykmldqvoetzsd`, empty/unrelated schema) than the one this repo's `.env`/`supabase/config.toml` actually points to (`kmighupzxdtulaqzcgqn`). I did not force it through — applying a migration to a Postgres project only nominally related to this codebase would be reckless. **A human with access to project `kmighupzxdtulaqzcgqn` must run this migration** (Supabase SQL editor or CLI) before the new `inquiries`/`rate_limits` tables and domain/project enum values exist in production.
- **`npm`/`bun install` reaches a private package mirror** (`europe-west1-npm.pkg.dev`) that this sandbox's network egress cannot reliably reach. Worked around it by fetching the exact pinned versions from the public npm registry directly and extracting them into `node_modules` **without touching the committed lockfile** — this got a full, clean `vite build` (client + Cloudflare Worker/Nitro SSR bundle) and `tsc --noEmit` running end-to-end against the real dependency tree, which is why the matrix below can say BUILD: PASS with real evidence rather than "looks right."
- Everything requiring a live, deployed app with a real domain (DNS, TLS, actual go-live, Stripe, full E2E customer journey, cross-browser/device manual QA) is out of reach in a sandboxed code session and is marked NO / MANUAL below, honestly.

## NO-GO

This is **NO-GO** for connecting the final custom domain today. The blocking items are exactly the ones no code session can complete on its own:

1. The migration above has not been applied to the actual connected Supabase project (`kmighupzxdtulaqzcgqn`) — this session's database access was scoped to an unrelated project.
2. No production domain exists yet, so DNS, TLS, live-HTTPS verification, absolute canonical/OG URLs, and the sitemap's final absolute-URL pass are all correctly left incomplete rather than faked.
3. Mobile/cross-browser/accessibility and the full customer E2E journey (signup → onboarding → payment → generation → domain → launch) need a real deployment and a human tester — nothing here was silently marked PASS without that evidence.

**READY FOR GO-LIVE** applies only once: the migration is applied, a real domain is connected and its apex/www DNS + TLS are verified live by `adminVerifyAndGoLive` (or equivalent manual check), `SITE_URL` is set, and a human has walked the full E2E flow on a live deployment across the required devices/browsers.
